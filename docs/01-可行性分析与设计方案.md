# Edifier Center — MR5 音箱 Windows 托盘控制程序
## 可行性分析与设计方案（v0.3.1 定稿）

> 日期：2026-11-01（v0.3.1：App 截图分析 §2.2.5、决策记录 §7；v0.3：需求与技术选型定稿；v0.2：MR5 逆向项目调研 §2.2.4）
> 目标硬件：Edifier MR5（三功放监听音箱，下称"音箱"）
> 现有音频链路：PC → Focusrite Scarlett 4i4 (4th Gen) → XLR → MR5（**保持不动**）
> 目标：Windows 任务栏托盘程序，展示音箱状态（音量/输入源/EQ 等）并进行简单控制，能力对齐手机 EDIFIER ConneX App 的常用功能。

---

## 1. 结论先行（TL;DR）

**可行，推荐立项。** 核心依据：

1. MR5 属于漫步者 **EDIFIER ConneX** App 控制的产品家族，控制通道是**蓝牙低功耗（BLE GATT）**，与音频流（A2DP）完全分离。这意味着控制通道可以和你的 XLR 音频链路并存，互不干扰。
2. 该协议家族**已有多份 2026 年的高质量逆向成果**（M60/M90、S880DB MKII），帧格式、GATT 服务骨架、核心命令（音量/输入源/EQ 预设/自定义 EQ/能力查询）全部有实机验证，且都有可直接运行的 Python 参考代码。更关键的是（v0.2 新增）：**已找到两个直接针对 MR5 的开源实现**（含一个 Windows 托盘程序），MR5 的服务 UUID、音量上限、9 段 EQ 布局、房间补偿协议全部确认（§2.2.4），MR5 需要补的只剩输入源 ID 映射。
3. Windows 端 BLE 技术栈成熟（WinRT API / Python bleak），托盘程序无技术障碍。

**一个需要实机确认的行为**（Phase 0，约 1 小时）：ConneX 音箱的 BLE 广播/暴露条件因型号而异（M60 实测空闲时可能不广播）。omarchy 项目实测 MR5：**无需系统级蓝牙配对**，首次扫描把音箱用背面按键置入配对模式即可，地址随后缓存；EdifierControl 在 Windows 上提供了配对/重连兜底。因此 PC 端策略为：程序维持**单条长活 BLE 连接 + 自动重连**，首次连接引导用户按键。具体表现以 Phase 0 冒烟测试为准（§4）。

### 1.1 需求定稿（v0.3，依据用户 2026-11-01 反馈）

- **显示（只读）**：当前输入源、输出状态（音量/静音）、连接状态、固件版本。
- **控制**：音量（含静音）、EQ（声音模式预设 + 9 段自定义 EQ）；声学调谐（低切/房间补偿，协议已逆向）作为同类调节放 M2。
- **明确不做**：固件更新/OTA、输入源切换（仅显示）、设备改名、LDAC 偏好、LED、关机、AVRCP 媒体控制。
- **形态诉求**：美观、资源占用少、符合 Windows 规范的轻量托盘程序 → 技术选型定稿见 §5.2（C# + WPF）。

## 2. 调研结果

### 2.1 MR5 官方信息

- 官方产品页：https://www.edifier.com/global/p/studio-monitors/mr5
- 接口：XLR / 6.35mm TRS / RCA / AUX，蓝牙 6.0（LDAC + SBC），支持**两台音频设备多点连接**
- App：**EDIFIER ConneX**（Android/iOS）——播放控制、音效切换与自定义 EQ、房间补偿（Room Compensation）设置
- 重要推论：多点音频连接意味着"手机保持音频连接 + PC 保持控制连接"这类混合场景有官方设计空间，但 **BLE 控制通道允许几个中心设备（central）同时接入仍未知**（风险 R2）。

#### 2.2.1 协议家族共性（两个型号完全一致）

**GATT 结构**（服务 UUID 前缀 `4809`，特征码全家族统一）：

```
service   4809xxxx-1a48-11e9-ab14-d663bd873d93     ← xxxx 每型号不同（M60=f601, S880DB=f101）
  char    48090001-1a48-11e9-ab14-d663bd873d93     [read, notify]   音箱 → 主机（状态推送）
  char    48090002-1a48-11e9-ab14-d663bd873d93     [write, write-no-resp]  主机 → 音箱（命令）
```

**帧格式**（校验和 = 前面所有字节之和的低 8 位）：

```
主机→音箱:  AA EC <CMD> <LEN_HI> <LEN_LO> <PAYLOAD...> <CHECKSUM>
音箱→主机:  BB EC <CMD> <LEN_HI> <LEN_LO> <PAYLOAD...> <CHECKSUM>
```

**连接仪式（必须，否则写入被静默忽略）**：
1. 对 `48090001` 写 CCCD（`01 00`）开启通知；
2. 发能力查询 `AA EC D8 00 00 6E`；
3. 之后即可发命令。官方 App 还会每隔几秒轮询 `C9/C3/68/61/D5/66`。

**核心命令**（两型号均验证）：

| 功能 | 查询 | 设置 | 备注 |
|---|---|---|---|
| 输入源 | `0x61`（group+source） | `0x62` | group 字节**每型号不同**；变更时音箱主动推送 |
| 音量 | `0x66` → `<最大值><当前值>` | `0x67` | 最大值每型号不同；旋钮转动也推送 |
| EQ 预设 | `0xD5` | `0xC4` | 切换时主动推送 |
| 自定义 EQ | `0x43` | `0x44`（单波段）/`0x47`（名称） | 带宽数量/布局每型号不同 |
| 播放控制 | — | `0xC2`（play/pause/next/prev） | 经由音箱转发 AVRCP，只在蓝牙输入下有意义 |
| 能力/状态 blob | `0xD8` | — | 22 字节静态能力表 |
| 设备名/固件 | `0xC9` / `0xC6` | `0xCA`（改名） | |

#### 2.2.2 型号间差异

| 参数 | M60 | S880DB MKII | M90 | MR5 |
|---|---|---|---|---|
| 服务 UUID 后缀 | `f601` | `f101` | 不同 | **`3a01`**（8625 版硬件为 `7e03`，见 §2.2.4） |
| 输入源 group/ID 表 | group `0F`：BT/USB/AUX = 01/02/03 | group `10`：USB/BT/光纤 = 01/04/05 | group `1D` | **group 及各输入 ID 待实测**（§4 Phase 0） |
| 音量最大值 | 16 | 30 | 50 | **30** |
| EQ 布局 | 6 段（62Hz–16kHz，6字节/段） | bass/treble 形态 | 9 段×4字节 | **9 段×4字节（eqIndex=12）：62/125/250/500/1k/2k/4k/8k/16k** |
| 房间补偿（声学调谐） | 无此功能 | 无 | 无 | **已逆向**（低切 20–100Hz、斜率 -6/-12/-18/-24 dB/oct、声学空间 0~-4dB、桌面补偿开关，见 §2.2.4） |

特征码 UUID（`48090001/0002`）、帧格式、连接仪式在两个型号上完全一致，MR5 大概率沿用——这正是"补参数"而非"从零逆向"判断的依据。

#### 2.2.3 关键实测经验（直接指导我们的设计）

- **BLE 可用性窗口**：M60 空闲时广播时有时无（90 秒扫描可能一无所获），GATT 可能暴露 0 个服务；S880DB MKII 明确**只有存在蓝牙 Classic 连接时才广播/暴露控制服务**，但 Classic 连接**不需要是当前输入**——音箱切到光纤/USB 时 BLE 控制依然可用。
- 音箱会**主动推送**状态：输入、音量（含物理旋钮）、EQ 变化都会通知——天然适合做实时状态同步。
- ACK ≠ 生效：输入切换要等 2–3 秒读回；LDAC 偏好写入可能导致 BLE+Classic 双双断连。
- 官方 App 的 Java 类名已被定位（`CommandManager.java`、`CommandParser.java`、`D8Bean.java` 等），反编译 ConneX APK 可快速获得 MR5 专属映射。

#### 2.2.4 MR5 直击：两个现成的 MR5 逆向实现（v0.2 新增，关键）

用户补充调研发现**两个直接针对 MR5 的开源实现**，MR5 协议从此基本完整（源码已存 `research/edifiercontrol/`、`research/omarchy-mr5/`）：

| | D4n13l3k00/EdifierControl | Devis99/omarchy-edifier-mr5 |
|---|---|---|
| 平台/形态 | **Windows 10/11 托盘程序**，C++20 + Dear ImGui/DX11，静态编译单 exe | Linux Omarchy（Quickshell 面板），QML + Python/bleak 守护进程 |
| MR5 支持 | MR3/MR5/MR4.5/MR4 MKII，标注 MR5 为"支持（ConneX v2 协议、9 段 EQ）" | 仅 MR5，注明"只在一台实机验证"，**协议从 ConneX App 逆向**（`com.edifier.lib_connect` 的 BLEManager/CommandManager/CommandBean + 解密的产品表 `products_release.json`） |
| 功能 | 音量 0–30+静音+滚轮 OSD、RSSI、EQ 预设、9 段自定义 EQ、低切/声学空间/桌面补偿、关机、LED、自启、睡眠唤醒重连（WM_POWERBROADCAST） | 音量（与物理旋钮/手机 App 实时同步）、Monitor/Music/Custom 模式、9 段 EQ 曲线拖拽、本地预设+分享码、声学调谐、固件版本显示 |
| 许可 | MIT（Releases 有现成 exe） | MIT |

**两个项目交叉确认的 MR5 协议事实**：

- 服务/搜索 UUID：标准版 MR5 搜索 `00003a01-0000-1000-8000-00805f9b34fb`、服务 `48093a01-1a48-11e9-ab14-d663bd873d93`；**存在 8625 DSP 硬件改版**（"MR5 (8625)"：`00007e03` / `48097e03`）——发现设备时要同时匹配两种。
- 特征码与其他型号一致（`...0001` 通知 / `...0002` 写入）。
- 帧格式：`AA <appCode> <CMD> <LEN_HI> <LEN_LO> <载荷> <校验和>`，响应头 `BB`（数据）/`CC`（ACK）/`DD`。**appCode 不是固定值**：omarchy 用 `0x06`（实测可用），EdifierControl 用 `0x0C`，M60/S880DB 文档观察到 `0xEC`——音箱对此字节不严格校验，实现时任取一即可。
- 音量：`0x66` 查询（返回 `<最大值><当前值>`，最大 30）/ `0x67` 设置；与物理旋钮双向同步（通知推送）。
- 输入源：`0x61` 查询（同样返回 `<最大值?><当前值>`）/ `0x62` 设置。**omarchy 明确说输入源 ID 映射没摸准、未实现切换**；EdifierControl 读取并显示输入状态，但源码中未发现 `0x62` 调用（README 宣称支持切换 BT/AUX/Line In，代码证据不足）。→ 输入源切换是唯一需要自己抓包标定的功能点。
- 自定义 EQ：`0x43` 查询 / `0x44` 单段设置。MR5 是 eqIndex=12 布局：9 段、每段 4 字节（索引+频率 2 字节+增益），62Hz–16kHz 倍频程。
- **声学调谐（房间补偿）已逆向**：挂在 `0xD5`/`0xC4` 的 EQ 帧尾部，7 字节载荷 `[mode][index][byte0][低切频率 20–100Hz 步进5][斜率索引 0-3 对应 -6/-12/-18/-24 dB/oct][声学空间 0-4 对应 0~-4dB][桌面补偿 0/1]`；omarchy 实机验证过解码（30Hz/-24dB/oct/-2dB/桌面开 = `02 02 00 1E 03 02 01`）。
- 连接行为：**无需操作系统级蓝牙配对/绑定**（与官方 App 一致，也意味着无鉴权——理论上可被伪造设备 spoof）；omarchy 首次扫描需把音箱置于**背面按键的配对模式**，地址随后缓存。蓝牙广播含厂商数据 ID `0x07E0`（Classic MAC + 协议版本 + 加密标志），广播名 `EDIFIER BLE`。
- 命令全集（EdifierControl 枚举）：`0x07` 复位、`0x43/0x44/0x45/0x46/0x47` 自定义 EQ 系、`0x61/0x62` 输入、`0x66/0x67` 音量、`0xC4` EQ+声学调谐、`0xC6` 固件、`0xCE` 关机、`0xD5` EQ 查询、`0xD6/0xD7` 自动关机、`0xD8` 能力、`0xF2` 设备状态、`0xF7/0xF8` LED。

**可直接借鉴的工程经验**：

- omarchy 的守护进程设计理由原文："per-command 重连对这颗音箱的 BLE 外设不可靠"→ **必须维持单条长连接 + 自动重连**，与 §5.3 设计一致。
- omarchy 遇到 BLE 重连不稳，提供"硬重连"（重启蓝牙适配器）兜底 → Windows 版同样要准备适配器级恢复手段。
- EdifierControl 的连接后首读序列：`66 / D5 / 43 / C6 / D8 / F2`；写队列 + WriteWithResponse；被动 RSSI 监听；待机/断线自动重连（含睡眠唤醒）。
- OTA 故意不实现（固件变砖风险），固件升级仍走官方 App——与我们 §3 R7 红线一致。

**对本项目的影响**：MR5 专属参数从"全部未知"变为"仅输入源 ID 映射待标定"，Phase 0 从"半天～1 天的协议逆向"缩减为"半小时冒烟测试"；同时出现一个新的决策选项——**直接使用现成的 EdifierControl.exe**（§7 新增问题）。

### 2.3 Windows 端开发生态

- **Python `bleak`**（https://github.com/hbldh/bleak）：跨平台 GATT 客户端，Windows 后端基于 WinRT，是事实标准；上面两个参考项目都用它，代码可大量复用。已知小坑：Windows GATT 缓存导致的偶发 "Unreachable"、服务发现时序问题，成熟的重连逻辑可覆盖。
- **C# .NET + CsWinRT**（`Windows.Devices.Bluetooth.*`）：Windows 原生 BLE API，托盘/WPF 体验最好，可发布单文件 exe。
- 托盘 UI：Python 侧 `pystray`/`rumps` 类方案 + Tk/Qt 弹窗，或 C# `NotifyIcon`/WPF Popup。

| R5 | PC 蓝牙适配器存在性/质量未知（4i4 不含蓝牙） | 低 | 用户确认；不行则购 USB BLE 5.0 适配器（约 ¥20–50） |
| R6 | Windows BLE 栈怪癖（GATT 缓存、偶发 Unreachable）；omarchy 实测重连可能不稳 | 中 | 参考两项目的实践：Uncached 读取、单长连接、指数退避、适配器级"硬重连"兜底 |
| R7 | 未知 opcode 可能触发危险操作（恢复出厂 0x07/OTA/解绑）；OTA 有变砖风险 | — | **安全红线**：只发已验证命令，绝不盲扫；OTA/固件类操作永远留给官方 App |

## 4. Phase 0：验证计划（v0.2 缩减：约 1 小时）

> v0.1 的 Phase 0 是"从抓包逆向 MR5 协议"（0.5–1 天）。§2.2.4 的两个项目把协议摸清后，现在只需冒烟测试。

目标：确认你这一台 MR5 在你的 PC 上可被控制，并标定输入源**显示标签**（v0.3 范围只显示不切换，无需抓包逆向 `0x62`）。

1. **零开发验证（可选但建议）**：下载 [EdifierControl Releases](https://github.com/D4n13l3k00/EdifierControl/releases) 的 exe 跑一次，确认 PC 蓝牙与这台 MR5 兼容。注意界面是俄语。
2. **自研冒烟测试**（临时 Python 脚本 `pip install bleak`，或直接用 M1 的 C# 骨架）：按服务 UUID `48093a01`（及 `48097e03`）扫描 → 连接 → 开通知 → 发 `66/D5/43/C6/D8/F2` 读回全部状态 → 设置一次音量并确认推送。首次扫描若扫不到，按音箱背面键进配对模式。
3. **并发测试**：PC 保持 BLE 控制连接时，手机 ConneX App 能否同时连？手机蓝牙音频连接着时 PC 能否控制？
4. **只读标定**（均为只读或可随手恢复的操作）：① 输入标签——在手机 App 里把输入依次切到各档，同时探针读 `0x61`，记录"字节 → 名称"对照；② EQ 增益换算——在 App 里把某一波段调到 0dB 和已知 dB 值各一次，读 `0x43` 记录字节值，验证 `(code−6)×0.5dB` 假设。
5. **产出**：Go/No-Go 结论 + `mr5.json` 定稿（预填 §2.2.4 已知值 + 输入标签表 + 增益换算）。

安全红线不变：只发上述已验证命令；不碰 `0x07`（复位）、OTA、解绑类操作；实验中改动的设置随手恢复。

### 5.2 技术选型（v0.3 定稿：C# / .NET 10 + WPF）

**推荐方案：C# / .NET 10 (LTS) + WPF + WPF-UI + H.NotifyIcon.Wpf，BLE 直接用 Windows Runtime API（TFM 设为 `net10.0-windows10.0.22621.0`，即 CsWinRT，无第三方 BLE 依赖）**

| 候选 | 空闲内存（约） | 安装体积 | Win11 原生观感 | 开发成本 | 结论 |
|---|---|---|---|---|---|
| **C# .NET 10 + WPF + WPF-UI** | 50–80 MB | 自包含单文件 ~70–90MB；依赖框架版 ~5MB | 高：Fluent 控件 + Mica/亚克力 + 亮暗跟随 | 中低 | **推荐** |
| C# + WinUI 3（Windows App SDK） | 100–150 MB | +约 50MB 运行时 | 最高（真 Fluent） | 中高（无内置托盘需绕行、打包复杂） | 资源超支，过重 |
| C# + WinForms | 30–50 MB | ~50MB | 中（全手绘） | 低 | 美观上限不足 |
| C++20 + Win32/ImGui（EdifierControl 路线） | 10–20 MB | 1–3MB | 低（游戏风，非 Fluent） | 高 | 极致轻量，但自研成本高；轻量需求可直接用它的现成 exe |
| Tauri v2 / Web 栈 | 面板打开 100MB+（WebView2） | ~10MB | 中（可仿 Fluent） | 中 | 内存随面板开关波动，与常驻托盘场景不匹配 |
| Python + bleak + pystray/Qt | 120–200 MB | 40MB+（PyInstaller） | 低 | 最低 | 原型快，但常驻资源、杀软误报都吃亏 |

选型理由（对齐"美观、轻量、符合 Windows 规范"三项诉求）：

- **美观**：[WPF-UI](https://wpfui.lepo.co/) 是把 Win11 Fluent 设计语言带进 WPF 最成熟的库——原版 Fluent 图标、圆角、Mica/亚克力背景、暗亮主题，托盘飞出面板观感接近系统原生设置面板；WinUI 3 观感更"正"但资源超支一倍。
- **轻量**：WPF 单实例空闲约 50–80MB，高于 C++ 但远低于 Web/Python 系，对 16GB+ 开发机无感；执行下方优化清单可压至 ~40–60MB。
- **符合 Windows 规范**：托盘 flyout 交互、原生右键菜单、随系统亮暗主题、DWM 圆角/Mica、单实例、自启走 Startup 文件夹（任务管理器可直接启停）、无后台服务、无需管理员权限、无通知打扰。
- **BLE**：与 EdifierControl 用同一套系统 API（`Windows.Devices.Bluetooth.*`），托盘用 [H.NotifyIcon.Wpf](https://github.com/HavenDV/H.NotifyIcon)，MVVM 用 CommunityToolkit.Mvvm。
- **综合各项目优点**：连接状态机、连接后首读序列、睡眠唤醒重连、托盘滚轮调音量取自 EdifierControl；单条长连接 + 通知驱动状态同步、profile 配置化、EQ/声学调谐实现取自 omarchy；安全红线取自 M60/S880DB 协议文档。

**资源优化清单**（实现时执行）：单实例互斥；Release + ReadyToRun；`InvariantGlobalization`；工作站 GC（默认）；flyout 窗口常驻但折叠（二次打开瞬时）；EQ 展开区懒加载、用轻量滑条不引图表库；RSSI 被动扫描（`Passive`）且仅连接期间开启；状态同步以推送为主、后台轮询 ≥5s 仅保活对账；音量滑条命令 ~150ms 合并节流。

**构建与运行期数据**（2026-11-01 定稿）：本机仅 Python、无 .NET SDK——**本地只做静态编写，编译/测试/打包/发布全部由 GitHub Actions**（windows-latest + .NET 10）执行；产物为**自包含单文件 exe**；运行期数据（`config.json` / `logs\` / `diagnostics\`）落在 **exe 运行目录**（可移植式布局，发布说明需建议放到有写权限的用户目录）。详见 [03-代码设计文档](03-代码设计文档.md) §8/§11。

### 5.3 模块划分（C# / WPF，概览）

> 最终实现结构以 **[03-代码设计文档](03-代码设计文档.md) §2** 为准（拆分为 Core / Ble / App 三个项目，本树为概览）。

```
EdifierCenter/
├─ src/EdifierCenter/              # WPF 主程序（net10.0-windows10.0.22621.0）
│  ├─ App.xaml(.cs)                # 单实例互斥、主题跟随、全局异常兜底
│  ├─ Tray/                        # H.NotifyIcon：图标状态机(连接/断开/静音角标)、
│  │                               #   原生右键菜单、悬停滚轮调音量
│  ├─ Views/FlyoutWindow.xaml      # WPF-UI 飞出面板（失焦自动关闭、Mica 背景）
│  ├─ ViewModels/                  # CommunityToolkit.Mvvm，绑定 SpeakerState
│  ├─ Ble/
│  │  ├─ Discovery.cs              # 广播扫描：同时匹配 48093a01 / 48097e03（双硬件版本）
│  │  ├─ Session.cs                # 连接仪式(CCCD→首读 66/D5/43/C6/D8/F2)、命令队列(Channel)、
│  │  │                            #   指数退避重连、PowerModeChanged 睡眠唤醒处理
│  │  └─ GattIo.cs                 # WinRT GATT 封装（Uncached 读写/订阅，隔离以便测试/替换）
│  ├─ Protocol/
│  │  ├─ Frames.cs                 # AA/appCode/BB 帧编解码、校验和（纯逻辑，单测覆盖）
│  │  ├─ Commands.cs               # 命令封装：音量/EQ/自定义EQ/声学调谐/查询，ACK 关联
│  │  └─ Parsers.cs                # EQ（eqIndex=12 九段）、声学调谐 7 字节、状态帧解析
│  ├─ State/SpeakerState.cs        # 状态存储 + 变更事件（UI 只读订阅，命令走 Session）
│  └─ Profiles/mr5.json            # 型号参数：UUID、音量上限 30、EQ 布局、输入标签表（Phase 0 标定）
├─ tests/EdifierCenter.Tests/      # 协议层单元测试（对照参考项目公开的实测帧）
├─ research/  docs/                # 已建立的调研资料
└─ README.md
```

**设计要点**

- **型号参数配置化**：所有"每型号不同"的东西（服务 UUID 后缀、输入源表、音量上限、EQ 布局）放 `mr5.json`，代码只认协议骨架。将来支持其他 ConneX 音箱 = 加一个 profile。
- **状态同步靠推送，不靠轮询界面**：`0x61/0x66/0xD5` 的主动通知覆盖"手机 App 改了音量 / 拧了物理旋钮 / 切了输入"全部来源；后台仅按官方 App 节奏（数秒一次）轻量轮询做保活与对账。
- **命令节流与读回确认**：滑条拖动时 0x67 命令合并节流（~150ms）；设置后不盲信 ACK，延迟读回（输入源切换需 2–3s 稳定期）。
- **连接生命周期**：启动 → 扫描（服务 UUID 前缀匹配，不等广播名，M60 实测经常无广播名）→ 连接 → 仪式（CCCD + D8）→ 就绪；断线后指数退避重连；音箱关机/超范围时托盘显示灰态并静默重试。
- **安全红线进代码**：命令白名单，仅暴露已验证 opcode；profile 里没有的命令 UI 不出现。

### 5.4 UI 设计（v0.3，Windows 11 规范，按需求定稿裁剪）

> 交互式设计稿已交付：**[docs/ui.html](ui.html)**（应用图标、托盘 4 状态、亮/暗弹窗、右键菜单、动效规格、渲染性能预算、功能核对），可交互演示，控件与 WPF-UI 一一映射，作为 M1 的 UI 实现基线。

```
                 ╭─────────────────────────────────╮
                 │  EDIFIER MR5BT          ● 已连接 │  ← 名称/状态点/RSSI；Mica 背景、圆角
                 │  输入源   XLR        固件 1.0.3  │  ← 0x61 只读徽章；0xC6 只读
                 ├─────────────────────────────────┤
                 │  音量                    22 / 30 │
                 │  ████████████░░░░░░░░   🔇      │  ← 0x66/0x67 滑条 + 静音
                 ├─────────────────────────────────┤
                 │  声音模式   (●监听) (音乐) (自定义)│  ← 0xD5/0xC4（档位名已由 App 截图确认）
                 │  ▸ 自定义 EQ（9 段竖向滑条）       │  ← 0x43/0x44，默认折叠，懒加载
                 │  ▸ 声学调校（低频切除/空间声学/    │  ← 0xC4 尾部 7 字节，默认折叠（M2）；
                 │      桌面反射控制）                │     术语对齐官方 App（§2.2.5）
                 ╰─────────────────────────────────╯
```

交互与规范细节：

- 托盘图标左键 → 面板锚定在托盘上方弹出；点击面板外部或 Esc → 自动关闭（`Deactivated` 处理），符合系统 flyout 习惯。
- 托盘右键 → **原生**上下文菜单：静音/取消静音、立即重连、开机自启（勾选）、退出。悬停图标滚轮 → 直接调音量（EdifierControl 同款，M3 可选）。
- 托盘图标状态化：正常（已连接）、置灰（断开/重连中）、静音角标。
- 托盘图标采用**应用图标微缩版 + 右下角状态点**（绿=已连接 / 灰=已断开 / 琥珀=重连中，静音叠加红色斜杠）——避免与系统音量的扬声器线稿混淆（2026-11-01 用户反馈修订）。
- "解码"徽章由音箱 `0x68` 状态**实时驱动**（05=有线 Hi-Res / 04=无线 Hi-Res / 00=标准，未知时不显示，断开显示"—"），不作为静态能力角标；0x68 已在官方 App 轮询序列中，无额外开销。
- 信号行将 RSSI 换算为档位显示（≥−55 优秀 / −55~−70 良好 / −70~−80 一般 / <−80 弱），括号内保留 dBm 原始值（RSSI = 蓝牙接收信号强度，负值越接近 0 信号越强）。
- 跟随系统暗/亮主题；面板宽约 360dp；所有状态变化（含物理旋钮、手机 App 的改动）经通知推送实时反映到面板——omarchy 已验证此体验。
- **UI 术语直接采用官方 App 中文命名**（监听/音乐/自定义、声学调校、低频切除、空间声学、桌面反射控制，见 §2.2.5），零学习成本。

MVP **不做**（依据 §1.1 需求定稿）：输入源切换（仅显示）、设备改名、LDAC 偏好、OTA/固件更新、LED、关机、AVRCP 媒体控制（`0xC2` 在 XLR 场景无意义）。

### 5.5 与现有音频链路的关系

- XLR 链路（4i4 → MR5）完全不经过蓝牙，程序只增加一条低速率 BLE 控制连接。
- 注意事项：PC 蓝牙设置里**不要把 MR5 设为默认播放设备**，避免系统声音意外走 BT；若 R1 验证结论是"必须保持 Classic 连接"，则把"保持已连接"作为程序的一项后台职责（检测掉线自动重连 A2DP 空闲链路）。
- 附带说明：输入切换不在范围（§1.1 定稿，仅显示）；想用手机蓝牙听歌时在手机 App 内切换即可。
